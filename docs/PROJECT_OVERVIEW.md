# PEAK Smart — 프로젝트 설명문 (브랜치 통합본)

> 출처: `https://github.com/Yzero56/Peak-Test` — `main`, `HJ`, `Wa`, `YJ`, `kang` 5개 브랜치를 종합.
> 목적: 이후 슬라이드 덱/애니메이션/라이브 데모 제작 단계에서 쓸 **단일 레퍼런스 문서**.

## 1. 한 줄 정의

**PEAK Smart — 냉장고가 유통기한을 대신 기억해주는 스마트 키친 서비스.**
사진 한 장으로 식품을 등록하면, AI가 식품명·유통기한을 읽고, 카메라·센서가 냉장고의 입출고를 자동으로 감지해 "오늘 먼저 먹어야 할 것"과 "남은 재료로 만들 수 있는 레시피"를 알려준다.

## 2. 문제 정의

- 식품을 살 때는 날짜를 보지만, 며칠 지나면 언제 샀는지·개봉했는지·언제까지 먹어야 하는지 잊는다.
- 문제는 "정보 부재"가 아니라 "기록의 지속 실패" — 매번 직접 입력해야 해서 습관이 유지되지 않는다.
- 결과: 음식은 냉장고 안에 남고, 정보는 기억에서 사라지고, 결국 버려진다.

## 3. 핵심 경험 — 3단계로 줄인 사용자 흐름

1. **찍는다** — 식품 라벨을 촬영 (또는 냉장고 문을 여닫기만 해도 카메라가 자동 촬영)
2. **확인한다** — VLM이 이미지에서 식품명·제조일·유통기한·보관방법을 구조화해 반환, 사용자가 검토
3. **안심하고 먹는다** — 앱에서 D-day, 온습도/가스 상태, 추천 레시피를 확인

설계 원칙: **새로운 습관을 요구하지 않는다.** 입력을 잘하는 사람이 아니라 "사진 한 번 찍는 사람"도 쓸 수 있어야 한다.

## 4. 신뢰 설계 (가장 강조되는 차별점)

- 라벨 날짜를 못 읽으면 AI가 임의로 값을 만들어내지 않고 **null로 남긴다.**
- 신뢰도가 낮거나 검토가 필요하면 **`needs_review`**로 표시.
- IN/OUT 판정도 확신이 낮으면 정답인 척하지 않고 **"애매함"**으로 정직하게 표시 (confidence < 0.5).
- 즉 AI가 모든 걸 자동 결정하는 게 아니라, 사용자가 마지막으로 확인하는 구조. **정확성뿐 아니라 불확실성까지 기록.**

## 5. 발표에서의 구분: CONCEPT vs ACTUAL DEMO

팀 발표 대본(원문)에 명시된 규칙 — 반드시 슬라이드 제작 시에도 유지할 것:

> `CONCEPT`는 전체 제품 경험, `ACTUAL DEMO`는 현재 저장소에서 실제 시연 가능한 기능으로 구분해서 말한다.

- **CONCEPT (비전)**: 냉장고를 열기 전에 오늘의 한 끼를 준비, 완전 자동화된 입출고 인식, 완성된 레시피 추천 앱
- **ACTUAL DEMO (현재 시연 가능)**: 문 열림 감지 → IN/OUT 판정(정확도 73%), 용기 종류 분류(94.1%), 사진 업로드 → VLM 분석 → 대시보드 반영, Expo 앱 UI/알림/레시피 화면

## 6. 시스템 아키텍처 — 엔드투엔드 데이터 흐름

```
[냉장고 문]
   리드스위치 → 문 열림/닫힘 세션 시작/종료 (Part 1, YJ)
        │
        ▼
[ESP32-S3 Sense 카메라] (문틀 마운트, AP/STA 겸용 Wi-Fi)
   손 위치 추적(MediaPipe) → hand-free before/after 프레임 촬영
   diff 인코딩(전/후 변화량 R/B 색상) → 로컬 TFLite(Edge Impulse) 추론
        │  IN / OUT / hand_only 판정 (Part 1, YJ)
        ▼
[용기 종류 인식] (Part 2, Wa)
   YOLO-World로 물체 탐지·크롭 → DINOv2 임베딩 → 분류기(로지스틱 회귀)
   텀블러 / 반찬 용기 / 생수병 구분
        │
        ▼
[백엔드: FastAPI + PostgreSQL] (Part 3, kang)
   이미지 저장 → 분석 작업 큐 등록 → VLM 호출(OpenAI 호환 adapter, Mock adapter 지원)
   VLM 응답(식품명/제조일/유통기한/보관방법) 정규화 → fresh/expiring_soon/expired/unknown 계산
   감지 이벤트 + 센서 데이터 API, 용기 재식별 이벤트, 자동 입출고 이벤트
        │  REST API (/api/v1/...)
        ▼
[앱: Expo + React Native + NativeWind] (Part 4, HJ)
   재고 D-day 시각화, 온습도·가스 상태(BME680), 알림, 오늘의 추천 레시피
```

### 파트 간 연동 계약 (실제 구현된 API 매핑)

- Base: `http://localhost:8000`, prefix `/api/v1`
- `GET /api/v1/dashboard/summary` → `display_name`, `expires_at`, `days_remaining`, `expiry_status`(fresh/expiring_soon/expired/unknown), `can_cook`, `requires_confirmation`
- 사진 인식 흐름: `POST /api/v1/food-images` (multipart) → `POST /api/v1/analysis-jobs` → `GET /api/v1/analysis-jobs/{id}` (status=succeeded 대기) → `POST /api/v1/analysis-jobs/{id}/apply` → `GET /api/v1/dashboard/summary`
- 4번(HJ) 앱 필드 ↔ 3번(kang) API 필드 변환: `id:number→string(UUID)`, `name→display_name`, `expiresAt→expires_at`, `location→storage_type`(냉장/냉동/실온), `category` 값 매핑(유제품/육류·계란/채소/수산물/기타)
- 주의: 4번 자체 백엔드(`/api/inventory`, SQLite)와 3번 백엔드(`/api/v1`, PostgreSQL)를 동시에 켜면 재고 데이터가 갈라지므로 **하나로 통일해서 시연해야 함.**
- ESP32가 AP 모드일 때 폰이 ESP32 Wi-Fi에 붙어있으면 노트북 인터넷을 못 쓰는 경우가 있음 → VLM 호출(인터넷 필요)은 반드시 인터넷 되는 경로에서 수행.

## 7. 파트별 구현 현황

### Part 1 — 냉장고 IN/OUT 판정 (브랜치: `YJ`)

- **하드웨어**: XIAO ESP32-S3 Sense + OV3660 카메라 + 리드스위치. AP/STA 겸용 Wi-Fi(로컬 실습망·시연장 공유망 대응).
- **핵심 설계**
  - 손 위치 기반 동적 크롭(MediaPipe HandLandmarker) — 냉장고 전체가 아니라 손 닿은 선반만 비교
  - hand-free before/after — 손을 뺀 상태로 전/후 촬영해 방향 신호가 손에 가려지지 않게 함
  - diff 인코딩(좌우 이어붙이기 대신 변화량을 R/B 색으로 인코딩한 1장) — CNN이 "비교"를 학습하도록
  - Edge Impulse 전이학습(MobileNetV2, 96×96) + **로컬 TFLite 추론** → 인터넷 없는 AP 환경에서도 동작
  - 확신도 낮으면 "애매함"으로 표시(threshold 0.5)
- **결과**: held-out 74장 기준 **정확도 73.0%** (baseline 33.3% 대비 +39.7%p). hand_only 100%, in 62.5%, out 75.8%.
- **한계**: 학습 데이터 작음(~380장), 방향(순서) 민감도 불완전(swap 테스트 절반만 뒤집힘), 문 빠른 연속 개폐 시 세션 혼선(1.2초 가드로 완화).

### Part 2 — 용기 종류 분류 (브랜치: `Wa`)

- **파이프라인**: YOLO-World(물체 탐지·크롭) → DINOv2 ViT-S/14(384차원 임베딩) → 로지스틱 회귀(클래스 불균형은 class_weight=balanced)
- **1차 실험 결과**: 검증 89.5%, 독립 시험 **94.1%**(16/17, 텀블러 7/7, 반찬용기 9/10). 시험 물건은 학습 때 안 본 것으로 분리.
- **실제 냉장고 재검증**(YJ 협업): 문틀 마운트 카메라로 새로 찍은 사진 기준 **탐지·분류 100%**(다만 표본 1장으로 참고용).
- **한계**: 실제 물건 종류가 적음(반찬용기 7종/텀블러 4종), 시험셋도 17장뿐 — 94.1%를 최종 정확도로 해석하면 안 됨. 손에 든 상태·실냉장고 배경 확장 검증 필요.

### Part 3 — 백엔드 / 데이터 / VLM (브랜치: `kang`, part 3·4)

- **스택**: FastAPI + PostgreSQL(Alembic 마이그레이션), Mock VLM adapter + OpenAI 호환 VLM adapter(factory 패턴)
- **구현 범위**: 식품 CRUD API, 이미지 업로드/저장, 분석 작업 큐, 유통기한 상태 계산(fresh/expiring_soon/expired/unknown), 감지 이벤트·센서 데이터 API, 용기 재식별 이벤트 연동, 냉장고 자동 입출고 이벤트 자동화
- **테스트**: expiry 계산, food/cooking 서비스, VLM factory, storage 등 단위 테스트 다수 보유(`tests/`)
- **다음 단계로 명시된 것**: 실제 VLM 호출 테스트, 대시보드 요약 API 확장, 프론트-백엔드 전체 흐름(E2E) 검증

### Part 4 — 앱 (브랜치: `HJ`)

- **스택**: Expo + React Native + NativeWind
- **화면/기능**: 재고 D-day 시각화, 도어/가스 센서 상태, 알림, 오늘의 추천 레시피, 유통기한 달력 선택, 설정 화면에서 백엔드 주소/토큰 입력(팀원 공유 백엔드 or 로컬 백엔드 선택 가능)
- **하드웨어 연동**: 카메라 보드에 BME680 온습도·가스 센서 I2C 연동, 리드스위치로 실시간 탐지·카메라 전원 자동 on/off, 라이브 뷰
- **백엔드 관리**: 자체 대시보드(KST 시각, 온습도·가스 실시간 갱신, 가스 추세 기반 이상 감지), Wi-Fi 재연결 드라이버 충돌 방지, 재고 API 연동 + EAS 배포 설정
- **주의**: 기본은 목업 데이터(`src/data/mock-fridge-data.ts`)로 즉시 구동 가능 — 클론 후 `npm install && npx expo start`만으로 UI 확인 가능. 실 데이터 연동은 설정 탭에서 백엔드 주소 입력 필요.

## 10. 통합 시 남은 과제 (팀에게 그대로 전달 가능)

- **백엔드 이원화 정리**: HJ 자체 백엔드(`/api/inventory`, SQLite, 숫자 ID) vs kang 백엔드(`/api/v1`, PostgreSQL, UUID) — 시연 전 반드시 하나로 통일. (kang 문서 기준으로는 이미 HJ 앱의 `src/lib/api.ts`를 3번 계약으로 교체 완료했다고 기록되어 있음 — 실제 브랜치 머지 시 재확인 필요)
- **네트워크 의존성**: ESP32 AP 모드 ↔ VLM(OpenAI, 인터넷 필요) 동시 사용 불가 문제 — 라이브 데모 환경(공학 1관 공동강의실)에서 Wi-Fi 토폴로지를 사전에 확정해야 함.
- **정확도 한계 정직하게 전달**: IN/OUT 73%, 용기 분류 94.1%(표본 적음) — 발표 시 과장하지 말고 "애매함/needs_review" 같은 신뢰 설계로 포지셔닝.
- **인증**: kang 백엔드는 현재 개발 단계라 인증 없음 — 데모 환경에서 외부 노출 시 유의.
